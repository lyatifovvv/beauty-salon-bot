# ADR 0012: Миграция на PostgreSQL для Production

## Context and Problem Statement
Изначально проект использовал SQLite (ADR 0003) для быстрого старта и локальной разработки. Однако, перед деплоем бота на облачные серверы (Render, Railway, Fly.io) использование SQLite создает риски потери данных, так как файловая система на бесплатных тарифах часто является эфемерной (стирается при перезагрузке). Нам необходимо обеспечить надежное и персистентное хранение реляционных данных.

## Decision Drivers
* Необходимость надежного хранения данных (клиентов, записей, портфолио) при деплое в облако.
* Желание использовать бесплатные облачные решения для базы данных (Neon.tech, Supabase).
* Поддержка всех возможностей Prisma ORM без ограничений, присущих SQLite.

## Considered Options
* Оставить SQLite (требует сложной настройки постоянных томов, доступно не везде).
* **Мигрировать на PostgreSQL** (идеальная совместимость с Prisma, множество бесплатных облачных провайдеров).

## Decision Outcome
Выбран вариант **Мигрировать на PostgreSQL**. Мы изменим `provider` в Prisma Schema и подключимся к внешнему облачному серверу базы данных.

### Consequences
* **Good:** Данные в безопасности независимо от перезагрузок сервера с кодом бота.
* **Good:** Готовность проекта к полноценному production-деплою.
* **Bad:** Требуется наличие интернет-соединения для локальной разработки (так как база будет в облаке).

## Implementation Plan
1. Заменить `provider = "sqlite"` на `provider = "postgresql"` в `prisma/schema.prisma`.
2. Обновить переменную `DATABASE_URL` в файле `.env` на ссылку от Neon.tech или Supabase.
3. Удалить старые миграции SQLite (папка `prisma/migrations`).
4. Сгенерировать новые миграции для PostgreSQL командой `npx prisma migrate dev --name init_postgres`.
5. Перезапустить проект и убедиться в работоспособности.
