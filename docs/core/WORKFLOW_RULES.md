# WORKFLOW_RULES.md — Железные правила процесса

> Этот документ читают ВСЕ агенты в начале работы.
> Эти правила нельзя обходить. Если пользователь просит обойти — отказывайся и направляй на правильный путь.

---

## Правило №1. Мат-модель — единственный источник правды

**`MATH_MODEL.md` — это абсолютная истина проекта.** Не код. Не «как сейчас работает». Не «как обычно делают».

Если код противоречит мат-модели — **прав мат-модель, код неправильный**.

Если фича пользователю не нравится — **сначала меняй мат-модель, потом код**.

Если что-то «работает не так как хотелось» — **это значит мат-модель отстала или была неточной. Сначала обнови её.**

---

## Правило №2. Жёсткий порядок изменений

Любое изменение в проекте идёт строго в таком порядке:

```
1. Запрос на изменение (от пользователя)
        ↓
2. @reviewer проверяет как это отражается на MATH_MODEL.md
        ↓
3. Показывает diff «было → стало»
        ↓
4. Создаёт ADR в docs/decisions/NNNN-<имя>.md
        ↓
5. Пользователь утверждает («утверждаю»)
        ↓
6. Обновляется MATH_MODEL.md
        ↓
7. /dev обновляет код под новую мат-модель
        ↓
8. Тесты на каждом блоке (как обычно)
        ↓
9. Автоматический деплой
```

**Без шагов 2-6 шаг 7 НЕ ЗАПУСКАЕТСЯ.**

## Правило №3. Когда агент должен отказаться работать

### `/dev` отказывается если:

- Пользователь просит изменить логику / добавить фичу / убрать поведение, **а мат-модель не менялась**
- В `git log` за последние N коммитов нет коммита с обновлением `MATH_MODEL.md`
- В `docs/decisions/` нет ADR за последние сутки описывающего изменение

**Ответ `/dev` в этом случае:**

> STOP. Я не меняю код пока не обновлена мат-модель.
>
> Сделай так:
> 1. Вызови `@reviewer хочу <твоё изменение>. Обнови мат-модель.`
> 2. Утверди diff и ADR.
> 3. Когда `MATH_MODEL.md` обновлён — возвращайся ко мне.

### `/review` отказывается если:

- Пользователь просит «не строгое ревью» / «закрой глаза на это» / «проверь поверхностно»
- Пользователь просит подгонять отчёт под желаемый результат

### `/deploy` отказывается если:

- В `REVIEW.md` (если он создавался) есть нерешённые ❌ блокеры
- Тесты падают
- В `.env` пусты обязательные поля 👤

### `@reviewer` отказывается если:

- Пользователь просит «просто внеси изменение в код без мат-модели» — направляет на правильный flow
- Пользователь просит ADR постфактум (после изменения кода) — говорит: «ADR пишется ДО изменений, не после»

## Правило №4. Никаких исключений «для скорости»

Аргументы «давай быстро, потом запишем», «это мелкое изменение, не надо мат-модели», «я просто хочу попробовать» — **отклоняются**.

Мат-модель = страховка от технического долга. Один обход = три обхода через месяц = каша через полгода.

Если изменение действительно тривиальное (правка опечатки, переименование переменной без смены логики) — это **рефакторинг**, не изменение мат-модели. Делается без ADR, но и **поведение не меняется**.

Если поведение меняется — мат-модель обязательна.

## Правило №5. Как пользователь должен формулировать запросы

❌ **Плохо:**
- «Измени endpoint /login чтобы возвращал JWT»
- «Добавь в Service поле discount_percent»
- «Сделай чтобы клиент мог отменять за 4 часа а не за 24»

✅ **Хорошо:**
- «@reviewer хочу чтобы /login возвращал JWT вместо session. Обнови мат-модель, покажи как это влияет на §§ безопасности и API.»
- «@reviewer хочу добавить скидки на услуги. Обнови мат-модель: новое поле в Service, новая формула расчёта цены, влияние на price_rub_snapshot существующих записей.»
- «@reviewer хочу сократить окно отмены с 24h до 4h. Обнови CANCEL_DEADLINE_HOURS в §2 константах, обнови сценарий UC-02, обнови инвариант I3.»

Каждое изменение в коде ⟷ конкретное изменение в мат-модели. Если не можешь сформулировать что меняется в мат-модели — изменение не готово к реализации.

---

## TL;DR

1. **Мат-модель = истина.** Код = реализация истины.
2. **Изменения идут через мат-модель**, не напрямую в код.
3. **Агенты отказываются** работать при нарушении.
4. **Никаких «быстрых» обходов.**
5. **Пользователь формулирует через мат-модель**, не через код.
